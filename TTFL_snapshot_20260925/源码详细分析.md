# TTFL 当前源码详细分析

更新时间：2026-09-25

本文档基于当前快照中的 `source/` 源码进行静态分析，重点核对实际执行流程、信任流聚合、TMAA 监控、攻击模拟、实验可复现性，以及源码与论文叙述之间的一致性。

## 1. 系统总体结构

当前系统由 Flower 联邦学习、客户端 TMAA Sidecar、服务端信任管理和逐层鲁棒聚合四部分组成。

核心执行链路如下：

```text
客户端加载数据
    ↓
客户端本地训练
    ↓
Sidecar 监控 + 数据审计
    ↓
生成 Trust Report
    ↓
上传模型参数和 Trust Report
    ↓
服务端解析报告
    ↓
计算 TrustScore
    ↓
计算 ContentScore
    ↓
更新 HistPerf / RiskEMA
    ↓
状态判断：NORMAL / SUSPECT / QUARANTINE / BLACKLIST
    ↓
逐层筛选、裁剪和重新归一化
    ↓
生成下一轮全局模型
```

主要文件如下：

- `source/run_simulation.sh`：启动服务端、20 个客户端、数据库清理和日志管理。
- `source/server/server.py`：Flower 服务端入口、CIFAR-10 代理集和探针数据加载。
- `source/server/strategy.py`：TMAA 自定义聚合策略，负责四阶段审计和逐层聚合。
- `source/server/trust_manager.py`：TrustScore、HistPerf、RiskEMA、隔离和黑名单状态机。
- `source/server/contribution.py`：贡献度、一致性和 ContentScore 计算。
- `source/server/sensitivity.py`：逐层敏感度、层级准入阈值和裁剪上限。
- `source/Client/client.py`：客户端 Flower 接口、本地训练、ASR 测试和报告上传。
- `source/Client/dataset.py`：CIFAR-10 数据划分和 Non-IID 分组。
- `source/Client/engine.py`：本地训练和测试函数。
- `source/Client/poison/attack_wrapper.py`：标签翻转、后门、Clean-Label 和语义攻击。
- `source/Client/tmaa/sidecar.py`：Sidecar 监控、数据审计和 Trust Report 生成。
- `source/Client/tmaa/tee_sim.py`：软件模拟的 TEE 身份和签名接口。
- `source/Client/tmaa/monitor.py`：文件、资源和网络监控。
- `source/Client/tmaa/inspector.py`：客户端数据统计和特征审计。

当前修复分支还将 CIFAR-10 下载和 ResNet-18 预训练权重下载改为显式开关；主协议默认使用本地数据和随机初始化，避免实验启动时产生隐式网络依赖。

当前源码已经通过：

```bash
python -m compileall -q source
```

这只能说明 Python 语法检查通过，不等于完整实验已经在当前环境重新运行成功。

## 2. 启动脚本与实验配置

入口是 `source/run_simulation.sh`。当前配置为：

- 服务端地址：`0.0.0.0:8080`；
- 客户端总数：20；
- 联邦轮数：30；
- 使用数据库仿真监控：`USE_SIMULATION=1`；
- 4 个恶意客户端、16 个正常客户端；
- 服务端和客户端按 GPU 编号分配进程。

恶意客户端配置为：

| 客户端 | 攻击类型 | 投毒比例 | 目标标签 |
|---|---|---:|---:|
| C0 | `label_flip` | 0.5 | 默认 |
| C1 | `backdoor` | 0.2 | 0 |
| C2 | `clean_label` | 0.5 | 0 |
| C3 | `semantic` | 0.5 | 默认 |

启动脚本还设置了：

```bash
ENABLE_KNOWN_TRIGGER_PROBE=1
HEAVY_PROBE_ROTATE_MOD=1
```

这意味着当前实验启用了已知右下角和左上角触发器探针，并且重探针轮换条件非常激进。论文中必须明确区分“已知触发器研究模式”和“未知攻击检测模式”。

### 2.1 启动脚本中的工程风险

脚本将 Python 路径写死为：

```bash
PYTHON_BIN="/data1/anaconda3/envs/W1lsp0/bin/python"
```

这会导致代码无法直接在其他机器运行。

脚本还硬编码了远程 MySQL 地址、root 用户和密码：

```bash
host="202.113.76.179"
user="root"
password="root123456"
```

同样的配置还出现在 `source/Client/poison/db_manager.py` 和 `source/server/trust_manager.py`。这会造成：

- 敏感凭据泄露；
- 实验强依赖远程数据库；
- 无法在离线环境复现；
- 启动脚本会直接删除远程 `tmaa_server` 数据库。

应改成环境变量和本地配置模板，并把数据库清理动作改为显式实验选项。

## 3. 客户端训练流程

客户端主逻辑位于 `source/Client/client.py`。

每轮客户端执行以下步骤：

1. 接收并加载全局模型；
2. 启动 TMAA Sidecar；
3. 对本地数据执行审计；
4. 保存训练前参数，用于后续计算逐层更新量；
5. 本地训练 3 个 epoch；
6. 计算每层参数变化范数；
7. 测试正常分类准确率；
8. 测试标准后门和 Clean-Label ASR；
9. 停止 Sidecar；
10. 生成 Trust Report；
11. 返回训练后模型参数和 JSON 报告。

实际训练调用为：

```python
train(..., epochs=3, ...)
```

但 Trust Report 中写入的是：

```python
"epochs": 1
```

这是一个明确的元数据错误，会影响吞吐量审计和论文复现，应改为真实 epoch 数或从训练函数参数统一传入。

客户端返回的是整个 `state_dict`，包括模型参数和 BatchNorm 统计量。服务端在计算扁平更新向量时会过滤部分 BatchNorm 统计量，但最终逐层聚合仍然使用完整层列表。因此“用于检测的更新”和“用于聚合的更新”不完全一致。

## 4. 数据划分与 Non-IID 设置

数据处理位于 `source/Client/dataset.py`。

当前数据划分为：

- 共享公共池：5,000 张；
- Group A：客户端 0–9，近似 IID；
- Group B：客户端 10–14，Dirichlet `alpha=1.0`；
- Group C：客户端 15–19，Dirichlet `alpha=0.1`。

每个客户端最终使用：

```python
client_indices = pool_shared_indices.tolist() + exclusive_indices
```

因此同一批 5,000 张图像会被复制到全部客户端。这个协议可以称为“带公共基础池的混合异构划分”，但不能直接等同于客户端数据完全独立的标准 Non-IID 设置。

这种设计的影响包括：

- 客户端之间有大量重复训练样本；
- 诚实客户端更新方向更容易相似；
- 恶意和正常更新之间的差异可能被公共池稀释；
- 服务端更容易构造稳定的群体参考梯度；
- 实际 Non-IID 难度低于没有共享池的设置。

论文中应报告：公共池大小、是否提供给所有基线、公共池是否参与本地训练，以及移除公共池后的结果。

### 4.1 随机性问题

数据划分部分使用了固定种子，但以下环节没有统一设置随机种子：

- `random.sample()` 选择投毒样本；
- PyTorch 模型初始化；
- 服务端 `torch.randint()` 生成 Cutout 位置；
- `RandomApply` 和颜色扰动；
- 本地 DataLoader 的随机打乱。

因此当前源码不能自动保证多次运行得到相同结果。若论文报告多次独立种子均值，应在启动脚本中统一设置 Python、NumPy、PyTorch 和 CUDA 的随机种子，并把种子写入日志。

## 5. 攻击模拟

攻击实现位于 `source/Client/poison/attack_wrapper.py`。

### 5.1 标签翻转

`label_flip` 会将样本标签随机改成除原标签以外的其他类别。

`directed_label_flip` 当前只实现了标签 0 到标签 1 的特殊情况，并不是通用的 source-to-target 定向翻转。

### 5.2 标准后门

标准后门使用右下角 3×3 触发器：

```python
image[:, 29:32, 29:32] = 2.5
label = target_label
```

### 5.3 Clean-Label

Clean-Label 使用左上角触发器，只对原本属于目标类别的样本加入触发器，不改变标签。

### 5.4 ASR 测试

客户端会构造两套测试集：

- 右下角触发器测试集；
- 左上角触发器测试集。

但是服务端 `weighted_average()` 只聚合：

- `accuracy`；
- `asr`。

客户端返回的 `asr_clean` 没有进入全局指标聚合。因此日志中输出的总体 ASR 主要是标准右下角后门 ASR，而不是所有攻击类型的宏平均值。

论文需要分别报告：

- clean accuracy；
- label-flip 影响；
- standard backdoor ASR；
- clean-label ASR；
- semantic attack 指标；
- 混合攻击总结果及其定义。

## 6. TMAA Sidecar 与数据审计

Sidecar 位于 `source/Client/tmaa/sidecar.py`，主要负责：

1. 启动资源和网络监控线程；
2. 调用 `DataInspector` 扫描本地数据；
3. 汇总系统完整性、资源波动、数据统计和训练元数据；
4. 调用模拟 TEE 生成签名。

数据审计位于 `source/Client/tmaa/inspector.py`，包含：

- 标签熵；
- 唯一样本比例；
- 初始适应损失；
- 特征类内方差和类间距离；
- 像素均值和标准差；
- K-Means + silhouette score 后门指标；
- 标签分布摘要。

### 6.1 “零知识审计”表述不准确

当前代码是客户端本地计算统计量，然后把统计摘要上传给服务端。它不是密码学意义上的零知识证明，也不能阻止恶意客户端伪造这些统计值。

更准确的论文表述应是：

> 客户端侧统计审计与摘要上报。

如果要保留“零知识”表述，需要额外实现可验证证明，而不仅是 JSON 字段。

### 6.2 后门聚类指标是启发式指标

`calc_backdoor_indicator()` 使用模型 logits 作为聚类特征，然后对目标类别做二类 K-Means。它没有直接验证两个簇是否分别对应干净样本和触发样本，且只分析有限数量的样本。

因此它只能作为启发式风险信号，不能直接解释为后门检测概率或 TPR。

### 6.3 差分隐私实现不完整

审计报告中的大部分指标使用 `epsilon=1000`，几乎等于不加噪声；标签计数又使用 `epsilon=5`。代码没有给出：

- 敏感度证明；
- 多轮隐私预算累计；
- 不同字段的预算分配；
- 组合隐私分析；
- 截断和裁剪机制。

论文中不宜笼统声称“实现了严格差分隐私”。

## 7. TEE 和系统监控问题

### 7.1 当前 TEE 是软件模拟

`source/Client/tmaa/tee_sim.py` 中的签名实际是：

```python
sha256(payload + self._private_key_secret)
```

私钥是 Python 对象中的字符串：

```python
self._private_key_secret = f"hw_secret_key_for_{device_id}_@!#"
```

这不具备真实 TEE 的：

- 硬件隔离；
- 私钥不可导出；
- 安全启动；
- 远程证明；
- 可信代码边界；
- 防主机篡改能力。

论文应明确写成 simulated TEE 或 TEE-compatible interface。

### 7.2 服务端没有验证签名

客户端将如下字段放入返回结果：

```python
{
    "trust_report": report_payload,
    "signature": signature
}
```

但服务端解析时主要取出 `trust_report`，没有重新计算哈希，也没有执行公钥验签。因此流程实际上是：

```text
客户端生成签名
    ↓
签名随报告上传
    ↓
服务端不验证签名
    ↓
服务端直接使用报告字段
```

恶意客户端可以直接伪造：

- `file_tampered=False`；
- `throughput_check=NORMAL`；
- `network_anomalies=0`；
- 任意数据审计指标；
- 任意设备 ID。

### 7.3 文件完整性检查没有可信基线

`monitor.py` 中的 `check_file_integrity()` 只检查文件是否存在并计算当前哈希，没有与预先存储的可信哈希比较。因此文件内容被修改但文件仍存在时，系统不会识别出篡改。

### 7.4 网络监控目前基本不起作用

网络监控能够枚举 TCP 连接，但发现非法外联后的计数和日志代码被注释掉：

```python
# self.network_violations += 1
# print(...)
pass
```

因此报告中的网络异常字段通常一直是 0。

## 8. 服务端审计和聚合流程

核心逻辑位于 `source/server/strategy.py`。

### 8.1 Trust Report 解析

服务端先检查客户端是否已被黑名单拦截，然后解析 `trust_report_json`。没有报告的客户端直接被拒绝。

但是报告签名没有验证，`real_client_id` 也来自客户端返回的 metrics。真实状态主要使用 Flower 的 `cid`，但日志和探针轮换使用客户端上报的 ID，因此客户端可以伪造日志显示和部分轮换条件。

### 8.2 更新量计算

服务端从客户端获得训练后的 `W_new`，使用上一轮全局模型计算：

```text
ΔW = W_new - W_old
```

这是比直接比较绝对权重更合理的实现。

### 8.3 服务器干净参考梯度

服务端从 CIFAR-10 测试集每类取 50 张，共 500 张，构造 `proxy_testloader`。随后用服务器模型在这 500 张样本上额外训练一轮，生成 `g_root_clean`。

优点：

- 降低客户端集体操纵参考方向的风险；
- 为标签翻转和符号翻转提供方向基准；
- 使参考更新相对稳定。

风险：

- 依赖服务器持有带标签的干净数据；
- 使用测试集进行额外训练，存在测试数据泄漏；
- 基线方法如果没有相同代理集，比较不公平；
- 不符合严格的“服务器没有干净参考数据”设定。

论文应把它明确写成服务器端 clean proxy set assumption，并给出代理集规模、来源、是否与基线共享，以及没有代理集时的结果。

## 9. ContentScore 和信任评分

### 9.1 贡献度和一致性

`source/server/contribution.py` 中使用：

```text
S_contrib = 0.6 + 0.4 × cos(g_k, g_root)
```

因此：

- `cos=1` 时得分为 1.0；
- `cos=0` 时得分为 0.6；
- `cos=-1` 时仍得分为 0.2。

这能容忍长尾 Non-IID 客户端，但也会减弱反向更新的惩罚。

跨客户端一致性也使用相同的 0.6 底座，并以其他客户端的 TrustScore 加权。

ContentScore 使用非对称调和融合：

```text
ContentScore =
[(1 + β²) × S_consist × S_contrib]
/
[β² × S_consist + S_contrib]
```

其中 `β=2`，设计上更偏向保留具有主任务贡献但群体方向不完全一致的长尾客户端。

### 9.2 RawScore

`trust_manager.py` 中实现：

```text
RawScore =
TrustScore^3.0
× ContentScore^1.0
× HistPerf^0.5
```

随后策略层又乘以风险衰减：

```text
RiskFactor = (1 - RiskEMA)^power
```

当前 `power=1.0`。

所以真正的聚合权重经过了：

1. TrustScore 指数惩罚；
2. ContentScore；
3. 历史信誉；
4. RiskEMA 衰减；
5. 逐层阈值筛选；
6. 幸存者重新归一化；
7. 逐层 L2 裁剪。

论文必须给出最终有效聚合公式，否则读者无法根据论文公式复现源码行为。

## 10. HistPerf 和 RiskEMA 状态机

新客户端初始状态为：

```text
HistPerf = 0.5
RiskEMA = 0.25
```

### 10.1 HistPerf

HistPerf 根据 ContentScore 的相对排名和绝对下限更新：

1. 计算 ContentScore 的 Z-score；
2. 使用 sigmoid 得到相对信号；
3. 计算绝对质量信号；
4. 按 0.4/0.6 融合；
5. 使用 EMA 更新历史信誉。

连续低于 `0.26` 达到 5 轮后，客户端进入历史软隔离。历史软隔离主要影响参考梯度构造和聚合资格，不立即永久封禁。

### 10.2 RiskEMA

风险流包含：

- Trust Report 风险；
- 梯度风险；
- 探针熵风险；
- 时间波动风险；
- SVD 谱风险；
- 像素统计风险；
- 触发器风险；
- peer 风险；
- 符号一致性风险。

代码用最大通道风险构造瞬时风险：

```python
instant_risk = max(channel_risks)
```

然后使用 EMA 更新 RiskEMA。

这种方式的优点是异常不会被平均稀释，但缺点是某一个标定错误的通道可能直接影响整个风险状态。

### 10.3 状态升级

当前实现比论文中简单的四状态描述更复杂，实际包含：

- soft streak；
- hard streak；
- probe streak；
- trigger streak；
- pixel streak；
- peer streak；
- C1 trigger combo；
- C2 seed；
- C2 memory score；
- C2 quarantine streak。

主要升级路径包括：

```text
RiskEMA > 0.64 + 软门控
    → 风险隔离 / QUARANTINE

RiskEMA > 0.90 + 持续强证据
    → BLACKLIST

C1 触发器组合异常持续两轮
    → 快速 BLACKLIST

C2 漂移组合持续多轮
    → BLACKLIST
```

如果论文只写 NORMAL、SUSPECT、QUARANTINE、BLACKLIST 四种状态，而不写 C1/C2 组合条件，论文会低估实际算法复杂度，读者也无法复现黑名单结果。

## 11. 服务端主动探针

服务端每轮构造多种探针：

- ColorJitter；
- GaussianBlur；
- Cutout；
- 右下角触发器；
- 左上角触发器；
- avgpool 特征；
- Softmax 熵；
- SVD top-1 比例；
- 目标类别置信度。

重探针不一定覆盖所有客户端，而是根据以下条件触发：

- 风险隔离；
- 历史 RiskEMA 较高；
- 当前报告风险较高；
- 轮换抽检命中。

当可用样本不足时，代码会将探针离群阈值设为 999，从而关闭探针惩罚。这一回退行为应在论文中说明，否则读者会以为每轮每个客户端都经过同样的探针检测。

当前启动脚本开启了已知触发器探针，所以实验结果包含攻击模板先验，不应直接概括为完全未知后门检测。

## 12. 逐层敏感度和聚合

逐层敏感度在 `source/server/sensitivity.py` 中计算：

```text
S_privacy = exp(-τ × layer_index / total_layers)
S_utility = ||g_ref^l|| / max_norm
S_security = 1 - trust-weighted cosine similarity
```

综合敏感度为：

```text
S_total =
0.3 × S_privacy
+ 0.4 × S_utility
+ 0.3 × S_security
```

准入阈值：

```text
threshold_l = 0.05 + 0.15 × S_total
```

裁剪上限：

```text
clip_target = 2.0 / (S_total + 0.01)
```

每层聚合流程为：

1. 排除已软隔离或风险隔离客户端；
2. 保留 `RawScore >= threshold_l` 的客户端；
3. 对幸存者重新归一化；
4. 按层计算更新范数；
5. 执行动态 L2 裁剪；
6. 加权累加更新；
7. 用 `W_old + ΔW_global` 重建全局模型。

优点是实现了论文中的分层门控、幸存者重归一化和动态裁剪。

局限是：

- `S_privacy` 只是按层索引衰减，并非真实隐私风险测量；
- `S_utility` 依赖参考更新范数；
- `S_security` 依赖当前客户端群体共识；
- 阈值和权重均为手工超参数；
- 没有收敛性或鲁棒性理论保证；
- 高风险节点可能被多重机制重复惩罚。

因此更准确的定位是“启发式动态分层鲁棒聚合”，而不是已证明最优的分层优化方法。

## 13. 主要问题按优先级排序

### P0：直接影响安全性和论文可信度

1. TEE 签名生成但服务端不验签；
2. 私钥是 Python 字符串，不是真实硬件密钥；
3. 文件完整性只检查文件是否存在，没有可信哈希基线；
4. 网络违规计数逻辑被注释，网络监控基本不起作用；
5. 服务端使用 CIFAR-10 测试集构造并训练干净参考梯度；
6. 启动脚本和数据库模块硬编码远程 root 凭据；
7. 服务器端使用已知触发器探针，但论文没有明确分离研究模式和通用检测模式。

### P1：直接影响实验结果和可复现性

1. 实际训练 3 epoch，但 Trust Report 写 1 epoch；
2. `test()` 中 loss 除以数据集样本数，而不是按 batch 或样本数加权；
3. 服务端只聚合标准后门 ASR，没有聚合 `asr_clean`；
4. 攻击样本随机选择没有统一种子；
5. 服务端探针随机增强没有统一种子；
6. 所有客户端共享 5,000 张数据，改变了 Non-IID 难度；
7. 论文中的宏平均 ASR 与当前源码统计口径不完全一致；
8. 多个风险阈值没有校准数据和敏感性分析。

### P2：影响工程质量和解释性

1. 多处 `except Exception` 会吞掉审计错误；
2. `StatusReporter.update()` 会完全忽略数据库异常；
3. `global_probe_entropy` 是占位值，实际长期为 0；
4. 后门聚类指标是启发式结果，但变量名和论文描述容易让人误解为直接检测指标；
5. 客户端上报的 `real_client_id` 被用于日志和探针轮换，可能被伪造；
6. 远程 MySQL 依赖使离线复现实验困难；
7. Scheme A–K 逻辑叠加后分支很多，单个组件的因果贡献不容易解释。

## 14. 源码与论文叙述的对应关系

源码能够支撑的论文表述：

- 双流信任：`HistPerf` 与 `RiskEMA` 确实分离；
- TMAA Sidecar：确实存在监控、数据审计和报告生成流程；
- 多种攻击：代码确实支持标签翻转、后门、Clean-Label 和语义攻击；
- 状态管理：确实存在风险隔离、软隔离和黑名单；
- 逐层聚合：确实存在逐层敏感度、门控、重归一化和裁剪；
- 30 轮实验：服务端配置确实为 30 轮。

需要降级或补充限定的表述：

- “TEE 安全保障”应改成“TEE 仿真接口”或“TEE-compatible architecture”；
- “零知识审计”应改成“客户端侧统计摘要审计”；
- “secure aggregation”不准确，因为服务端查看每个客户端更新；
- “不依赖干净数据”不成立；
- “未知攻击泛化”不成立，因为实验开启了已知触发器探针；
- “严格差分隐私”缺少预算和组合分析；
- “edge-deployable”缺少端到端 TEE、通信、内存和客户端开销测量；
- “宏平均 ASR”必须与源码实际聚合指标重新对齐。
